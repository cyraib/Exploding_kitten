You are the final QA engineer, gameplay tester, UX reviewer, and implementation engineer for this Exploding Kittens web game.

Your job is NOT only to inspect the code.

Your job is to actually run the game, play it repeatedly, find problems yourself, fix them, retest them, and keep iterating until the game feels like a complete polished product.

## MAIN OBJECTIVE

Turn the current project into a stable, polished, enjoyable desktop Exploding Kittens game.

The game should feel like a real digital card game, not just a functional web prototype.

Do not stop after finding issues.

For every issue you find:

1. reproduce it,
2. identify the cause,
3. fix it,
4. run the game again,
5. verify the fix,
6. check that the fix did not break another feature.

Continue this loop until no important gameplay, UI, UX, animation, or state-management issues remain.

Do not rely only on reading source code.

Do not assume a feature works just because its code exists.

Actually trigger it.

# 3. GAMEPLAY VALIDATION

Check every important gameplay rule.

Verify:

- correct starting hands,
- correct Defuse distribution,
- correct number of Exploding Kittens,
- correct draw deck construction,
- turn order,
- drawing ends a normal turn,
- Attack correctly modifies remaining turns,
- stacked Attacks behave correctly,
- Skip consumes the correct number of turns,
- Favor targets the correct player,
- pair stealing works,
- triple stealing works,
- requested card handling is correct,
- Shuffle really changes deck order,
- See the Future shows the correct cards without modifying deck order,
- Nope cancels valid actions,
- Nope-on-Nope restores the cancelled action,
- Exploding Kitten resolution works,
- Defuse removes the immediate explosion,
- the Kitten is correctly reinserted,
- eliminated players cannot act,
- the last surviving player wins,
- game-over state cannot continue accidentally.

Look specifically for edge cases involving:

- Attack + Skip,
- Attack + another Attack,
- Attack + Nope,
- Defuse during multiple pending turns,
- target player dying before an action resolves,
- empty or nearly empty draw pile,
- card selection remaining active after state changes,
- animation finishing after game state has already changed.

Fix any incorrect rule behavior you discover.

---

# 4. BOT PLAYTESTING

Watch the bots carefully.

Bots must:

- take legal actions,
- never select invalid targets,
- never play impossible card combinations,
- understand pending Attack turns,
- use Defuse correctly,
- react correctly to Nope,
- make reasonable card choices,
- eventually end their turn,
- never get stuck.

Look for:

- infinite loops,
- bots doing nothing,
- instant actions that feel unnatural,
- actions happening in the wrong order,
- bots acting after elimination,
- bots acting during another player's interaction,
- bots interrupting animations incorrectly.

Add natural bot delays where useful.

Typical timing:

- simple decision: 400–800 ms,
- card play: 500–900 ms,
- target decision: 600–1100 ms,
- important decision: up to ~1400 ms.

Do not make the game unnecessarily slow.

---

# 5. UI / UX REVIEW

Evaluate the interface as if you had never seen the project before.

The player should always understand:

- whose turn it is,
- what just happened,
- what they can currently do,
- which cards are selected,
- whether they need to select a target,
- whether they need to draw,
- how many turns remain,
- whether a Nope window is active,
- whether an Exploding Kitten is being resolved.

Fix confusing UX.

Pay special attention to:

## Turn feedback

Make the active player obvious.

Use:

YOUR TURN

or

PLAYER NAME'S TURN

When Attack is active, clearly show:

2 TURNS LEFT

or the correct remaining count.

## Cards

Cards should have clear states:

- idle,
- hover,
- selected,
- playable,
- disabled.

Hover should feel responsive.

Selected cards should visibly lift above the hand.

Invalid combinations must not look playable.

## Draw pile

The draw pile should clearly communicate:

DRAW & END TURN

when appropriate.

Hover and click feedback should feel physical.

## Discard pile

The most recently played card should be clearly visible.

Played cards should animate toward the discard pile.

## Target selection

When an action requires another player:

- dim unrelated UI,
- highlight legal targets,
- show a clear instruction such as:

CHOOSE A PLAYER

Do not rely on the user guessing what to click.

## Contextual instructions

Replace generic help text when possible with contextual instructions.

Examples:

ATTACK — Give the next player 2 turns.

PAIR — Choose a player and steal 1 random card.

TRIPLE — Choose a player and request a specific card.

DRAW — Draw a card to end your turn.

# 6. ANIMATION REVIEW

Animations must communicate gameplay rather than exist only for decoration.

Check:

- card hover,
- card selection,
- card play,
- draw animation,
- discard animation,
- turn transition,
- target selection,
- bot action,
- Nope,
- Exploding Kitten,
- Defuse,
- elimination,
- victory.

Recommended timing:

small UI feedback:
150–250 ms

card movement:
250–500 ms

major card reveal:
500–900 ms

dramatic events:
700–1200 ms

Avoid excessive waiting.

Animations must never block game state permanently.

If an animation fails or is interrupted, gameplay must still recover safely.

---

# 7. EXPLODING KITTEN SEQUENCE

Treat drawing an Exploding Kitten as a major event.

Expected experience:

draw card
→ card moves toward center
→ card reveals
→ short dramatic pause
→ screen impact / shake / flash
→ EXPLODING KITTEN state appears

If the player has Defuse:

highlight the valid Defuse interaction clearly.

After Defuse:

Defuse resolves
→ explosion is cancelled
→ user chooses where to put the Exploding Kitten back into the deck
→ game resumes correctly.

If no Defuse exists:

resolve elimination clearly.

Do not immediately skip over this sequence.

---

# 8. NOPE INTERACTION

Test the Nope system carefully.

When a Nope-able action is played:

show:

- the action being challenged,
- a visible reaction timer,
- a clear NOPE button.

Ensure the game cannot accidentally continue before the reaction window resolves.

If another Nope cancels the first Nope, visually communicate that the original action is active again.

Make the state deterministic and safe.

---

Improve the existing design.

# 11. STATE AND BUG TESTING

Actively try to break the game.

Click quickly.

Click during animations.

Spam buttons.

Select and deselect cards rapidly.

Try to:

- double draw,
- double play,
- click disabled controls,
- select players at the wrong time,
- trigger actions while a modal is open,
- play while bot is thinking,
- play during the Nope window,
- reload during a game,
- reload during a special interaction.

Make state transitions resistant to accidental double input.

Prevent:

- duplicated actions,
- duplicated card draws,
- duplicated cards,
- lost cards,
- impossible hand counts,
- negative pending turns,
- multiple turn transitions firing simultaneously.
